# 协议、RPC 与消息传递漏洞挖掘

#### 何时使用本文件

当目标使用 gRPC、GraphQL 传输、Cap'n Proto、Thrift、Protobuf、自定义二进制协议、流式 RPC、Webhook、消息代理、队列、发布/订阅或事件总线时，使用本文件。本文件涵盖对等方身份、逻辑消息解释、路由、重放、排序和投递语义。解析器内存安全见 `MEMORY-SAFETY-AND-BINARY.md`，HTTP 帧处理见 `WEB-PROTOCOL-AND-AUTH.md`，可用性影响见 `RESOURCE-EXHAUSTION-AND-AVAILABILITY.md`。

按生产者/消费者对、外部/内部对等方角色、同步 RPC、流式和异步消息路径拆分大型系统。

## 核心准则（本领域每个 agent 提示词都必须包含）

```
- "内部"不等于认证。在每一跳指明对等方身份，并说明它如何成为用于授权的应用主体。
- Schema 校验只证明消息形状，不证明来源、资源权限、排序或值安全。追踪解码后的字段到策略和副作用。
- 消息代理的保证与应用层的保证不同。在评估状态变更前，先写明重试、排序、确认、去重和事务行为。
- 解析器分歧需要两个具体消费者、Schema 版本或线格式表示，以及一个安全相关的分歧值。
- 源码完整的路径加上有界的本地生产者/消费者测试，用 `confirmed`。消息代理 ACL、服务网格身份、主题挂载或仓库外的兼容行为，用 `needs_validation`。
```

## 帧处理、Schema 与解释攻击类（subagent_type: `general`）

**消息边界与规范化分歧**
各组件在长度、压缩、重复字段、未知字段、编码、数值宽度、规范化或信封/正文优先级上存在分歧。对比生成的解析器与自定义解析器、网关、语言绑定和版本转换器。确认解码后哪个主体、资源或操作出现差异。

**联合体、枚举与默认值混淆**
未知变体、缺失判别符、零值、默认权限或兼容映射进入假定已校验分支的代码。审查穷举分发、默认分支，以及旧消费者如何解释新增字段。

**信封与载荷身份不匹配**
授权使用看似可信的路由或信封元数据，而处理器却作用于正文中冲突的租户、账户、主体、对象或发送者。确定哪个来源是权威的，并确保客户端无法覆盖它。

## RPC 身份与授权攻击类（subagent_type: `general`）

**拦截器与方法路径不一致**
认证/授权拦截器作用于一元方法，但不作用于流、反射、健康检查、网关转码路径、兼容服务或单个流消息。将每个注册和路由与同一操作对比。

**对等方身份与应用主体混淆**
mTLS、工作负载身份、Bearer 元数据、转发身份或消息代理凭据认证的是通道，但调用方控制的字段选择用户或租户。通道身份与声称的主体必须由确定性策略绑定。

**逐项与流式授权缺口**
流、订阅、批量或群发消息只授权一次，后续项却指向不同资源，或在角色、成员资格或令牌撤销后继续。在作用域可能变化处重新检查，并将订阅绑定到其原始主体。

**回调与回复关联混淆**
可预测、复用或跨租户的关联 ID 使响应、Webhook、取消或确认满足另一调用方的待处理操作。将每个未完成请求绑定到已认证对等方、租户、操作和生命周期。

## 消息代理与队列隔离攻击类（subagent_type: `general`）

**主题、路由键与订阅作用域缺口**
发布者或订阅者可以选择另一租户的主题、通配符、消费者组、分区、回复队列或死信路由。检查可见的消息代理 ACL 和应用侧命名空间构造。载荷中的租户文本不构成隔离。

**死信、重试与诊断信息泄露**
路由到死信队列、错误主题、追踪或运维视图的消息包含机密或跨租户载荷，低信任消费者可访问。审查失败路径上的策略和脱敏，而不仅是正常投递。

**不可信生产者被当作控制平面**
消息正文可以自称管理事件、提供方回调、复制记录或迁移指令，而没有独立认证的生产者和事件类型。在特权处理前验证签名及来源/账户/受众绑定。

## 重放、排序与事务攻击类（subagent_type: `general`）

**重复投递与幂等性缺口**
重试或重投递重复副作用，因为缺少去重、去重发生在变更之后，或使用的键在租户或操作间冲突。确认消息代理的投递模型以及非天然幂等的副作用。

**乱序与过期消息接受**
较旧状态、已撤销成员资格、已取消工作或升级前授权在新状态之后到达并覆盖它。审查序列/版本检查、墓碑、分区变更和恢复/重放工作流。

**确认/提交顺序缺陷**
确认发生在持久提交之前，丢失安全相关工作；或提交发生在不可靠确认之前，重复变更。评估事务性发件箱/收件箱行为和故障恢复。

**多消费者部分转换**
多个消费者共同实现一个授权或业务转换，但重试和部分失败只提交了子集。识别必须原子持久化或用当前授权补偿的不变量。

## 通用方法（适用于以上所有内容）

- 为每个消息族绘制 生产者 → 消息代理/传输 → 网关 → 消费者 → 存储。在每一跳记录已认证对等方、权威租户/资源字段、校验和副作用。
- 将同一小型测试夹具喂给每个仓库内 Schema 版本或语言绑定。测试重复、缺失、未知、边界、重放和乱序消息，不产生负载。
- 对比正常、重试、死信、重放、迁移、反射、流和网关转码路由。安全策略必须在传输变化后仍然有效。

## 验证规则（在此报告任何发现前应用）

1. 指明现实的生产者或对等方、被接受的消息、已认证的通道身份、受影响的主体/资源，以及未授权的变更或泄露。
2. 对于分歧声明，引用两个解析器/消费者和分歧的解码值。任一侧的安全拒绝即可阻止确认。
3. 对于重放/排序声明，确定实际投递保证，并用有界的本地/内存传输复现不变量失败。
4. 对于授权和隔离，验证源码中所有可见的拦截器、消息代理 ACL、网关和消费者层。外部挂载使候选变为 `needs_validation`。
5. 仅在完整消息生命周期和观察到有意义结果时返回 `confirmed`。返回 `needs_validation` 时附上所需的确切消息代理、服务身份、路由或投递事实。
