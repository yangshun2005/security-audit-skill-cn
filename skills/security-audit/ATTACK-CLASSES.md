# 攻击类别

#### 攻击类别 — 基于阶段 1 选择并拆分

选择与应用类型相关的攻击类别。并非每个类别都适用于所有代码库。以下列表是起点；请从阶段 1 补充应用特有的类别，并按子系统拆分大型代码库。工作定位为发现、验证、修复漏洞并排定优先级。验证仅限于源码审查和有界本地夹具；不要开发载荷链、测试线上服务的可用性，或在共享环境中采取行动。

仅当源码证据和有界验证确立了完整边界和有意义的结果时，才使用 `confirmed`。当具体的部署、提供商、平台、身份或运行时事实不可用时，使用 `needs_validation`；说明缺失的事实，以及能解决该问题的、由所有者观察或本地执行的安全检查。

> **原生 / 二进制 / 内核目标**（C/C++/Rust-unsafe、内核模块、解析器和解码器、FFI、并发运行时、二进制加载器、JIT、固件）：使用 [MEMORY-SAFETY-AND-BINARY.md](MEMORY-SAFETY-AND-BINARY.md) 中的内存安全、整数/ABI、并发、二进制加载器和特权接口类别。
>
> **AI / LLM / 智能体目标**（聊天机器人、RAG、持久记忆、工具调用智能体、MCP 服务器/客户端、提示词组装或模型控制的操作）：使用 [AI-AND-LLM.md](AI-AND-LLM.md) 中的上下文、记忆投毒、操作绑定、工具 Schema、MCP 身份和输出类别。
>
> **HTTP、Web 和身份目标**（普通 Web 应用、API、反向代理、CDN、网关、自定义 HTTP 解析器、会话、CSRF、JWT、OAuth/OIDC、SAML、MFA、通行密钥、账户恢复/关联、API 密钥或 mTLS）：使用 [WEB-PROTOCOL-AND-AUTH.md](WEB-PROTOCOL-AND-AUTH.md)。
>
> **客户端和浏览器目标**（SPA、浏览器扩展、嵌入式 webview、Service Worker、浏览器存储、跨窗口消息、CORS、WebSocket 或 DOM 渲染）：使用 [CLIENT-SIDE.md](CLIENT-SIDE.md)。
>
> **供应链和发布目标**（依赖解析、生成的输入、CI、发布/签名/晋级、更新、插件或扩展）：使用 [SUPPLY-CHAIN-AND-RELEASE.md](SUPPLY-CHAIN-AND-RELEASE.md)。
>
> **云和部署目标**（IAM、基础设施即代码、容器/Kubernetes、服务网格、Serverless/边缘、入口、提供商事件或运行时配置）：使用 [CLOUD-AND-DEPLOYMENT.md](CLOUD-AND-DEPLOYMENT.md)。
>
> **协议、RPC 和消息目标**（gRPC、GraphQL 传输、Protobuf/Cap'n Proto/Thrift、自定义协议、队列、代理、发布/订阅、Webhook 或流式 RPC）：使用 [PROTOCOLS-RPC-AND-MESSAGING.md](PROTOCOLS-RPC-AND-MESSAGING.md)。
>
> **资源耗尽和可用性目标**（不可信工作可消耗共享 CPU、内存、磁盘、连接、工作线程、队列、配额或运营方承担的费用）：使用 [RESOURCE-EXHAUSTION-AND-AVAILABILITY.md](RESOURCE-EXHAUSTION-AND-AVAILABILITY.md)。
>
> **数据隔离和生命周期目标**（多租户存储、缓存/搜索、对象链接、分析、导出/备份、迁移、删除、保留或恢复）：使用 [DATA-ISOLATION-AND-LIFECYCLE.md](DATA-ISOLATION-AND-LIFECYCLE.md)。
>
> **桌面、移动和本地 IPC 目标**（原生应用、深度链接、webview 桥、导出的组件、特权辅助进程、本地守护进程、Unix socket/XPC/Binder/D-Bus）：使用 [DESKTOP-MOBILE-AND-LOCAL-IPC.md](DESKTOP-MOBILE-AND-LOCAL-IPC.md)。

**注入**（subagent_type: `general`）
追踪不可信输入从入口点到危险汇点。什么算"危险汇点"取决于应用：
- Web 应用：SQL 查询、HTML 输出、shell 命令、模板引擎、文件路径、HTTP 重定向、反序列化
- 库：任何处理调用方提供数据而不做验证的函数 — 缓冲区操作、解析器、格式化字符串
- CLI 工具：shell 命令构造、文件路径处理、环境变量插值
- 服务：查询构造、消息序列化、日志注入、LDAP/XPATH 查询
- 客户端（浏览器/JS）：DOM XSS、原型污染、`postMessage`/来源信任及其他浏览器端类别 — 选中时由 [CLIENT-SIDE.md](CLIENT-SIDE.md) 配套块覆盖

不要止步于明显的直接路径。寻找间接注入：数据安全存储后，被不同代码取出并用于危险上下文。寻找通过字段名、键、头部和元数据（而非仅值）进行的注入。寻找注入到次级系统（日志、缓存、搜索索引、分析）的情况。

**访问控制**（subagent_type: `general`）
验证调用方无法做超出其权限的事。不要只检查权限检查是否存在 — 要验证它们是否通过*正确*机制检查*正确*资源的*正确*权限：
- 是否存在检查不同（更弱）权限却导致相同状态变更的路径？
- 请求体中的字段能否覆盖权限系统本意限制的内容？
- 是否存在只做认证却忘记授权的端点？
- 同一资源是否有多个访问路径且检查不一致？
- 批量/批处理/导出/导入操作呢 — 它们是否执行逐项权限检查？

对于复杂访问模型，拆分为独立智能体分别处理认证绕过与授权逻辑。

**资源和文件处理**（subagent_type: `general`）
- 路径遍历（读写预期目录之外）— 包括通过符号链接、编码序列和空字节
- SSRF（使应用获取攻击者控制的 URL）— 包括通过重定向、DNS 重绑定和 URL 解析器差异
- 不安全反序列化、归档解压（zip slip）、临时文件处理
- 内存安全（如适用）：缓冲区溢出、释放后使用、整数溢出
- 文件操作上的竞态条件（检查与使用之间的 TOCTOU）

**密码学和密钥**（subagent_type: `general`）
- 安全关键值（令牌、密钥、nonce）的弱随机性
- 硬编码密钥、日志/错误消息/URL/客户端可见响应中的密钥
- 损坏的密钥派生、缺失 HMAC 验证、nonce 重用
- 密钥比较上的时序侧信道
- 密码学原语误用（ECB 模式、未认证加密、静态 IV 等）
- 密码学操作失败时会发生什么？错误路径是否回退到无加密？

**业务逻辑**（subagent_type: `general`）
手工寻找逻辑错误：标准扫描器找不到它们，且它们能产生高影响发现。对每个主要工作流：
- **状态机违规**：能否跳过步骤？倒退？到达无效状态？重放已完成的流程会怎样？部分失败呢 — 3 步中的第 2 步失败时，第 1 步是否回滚？
- **有业务影响的竞态条件**：产生无效状态的并发操作（双重花费、双重审批、丢失更新）。关注非原子地先检查后执行的操作。
- **数值/数量操纵**：负值、零值、溢出、精度丢失、字符串与数字间的类型强制转换。
- **访问边界违规**：不是"权限检查是否存在"，而是"它是否是该业务规则的正确检查？"一个操作的输入能否绕过对另一操作施加的限制以达到相同效果？
- **隐式信任假设**：来自存储、配置、其他组件或插件的数据因"我们在入口处验证过"而被假定安全。如果另一代码路径写入了它呢？
- **基于时间的逻辑**：过期检查、调度、速率窗口、时钟偏移。恰好在边界时刻会发生什么？组件间的时区差异呢？
- **默认和回退行为**：配置缺失时的安全态势如何？功能开关关闭时？依赖不可用时？系统处于迁移中途时？

**功能滥用和数据泄露**（subagent_type: `general`）
合法功能被用于非预期目的。寻找设计中的缺陷，而不仅是代码中的：
- **导出/备份作为外泄**：低权限用户能否触发包含超出其访问级别数据的导出、快照或备份？能否导出其他用户的数据？导出是否包含已删除/草稿/私密内容？本应被修剪的修订历史？
- **导入/恢复作为注入**：导入能否覆盖现有数据？能否创建绕过正常验证的记录？能否向用户无写权限的集合注入内容？它是否遵守与 UI 相同的权限模型？
- **搜索/过滤/排序作为预言机**：搜索查询能否揭示用户无法直接访问的内容是否存在？过滤参数是否让用户探测本不应知道的状态、角色或字段？按隐藏字段排序是否通过结果顺序泄露其值？
- **通过副作用的枚举**：错误消息在"不存在"和"无访问权限"之间是否有差异？响应时间？响应大小？HTTP 状态码？能否通过密码重置、邀请或注册流程枚举用户？
- **预览/草稿/预发布泄露**：预览令牌是否限定于单个条目，还是解锁更广的访问？草稿内容能否通过搜索、RSS 源、站点地图或 API 列表端点被发现？缓存头是否导致 CDN 公开提供私密内容？
- **通知/Webhook 作为 SSRF**：用户能否设置服务器会获取的通知 URL、Webhook URL 或回调 URL？是否针对内部网络验证？重定向之后呢？

**链式漏洞和信任边界**（subagent_type: `general`）
单独允许或受控的行为，当另一组件或生命周期步骤依赖更强保证时，可能成为漏洞：
- **多步边界失败**：梳理低权限主体可读、可写、可调用和可保留的内容，然后仅将具体输出连接到后续信任决策。确认每个前提，不要假定下游效果。
- **跨组件信任缺口**：组件 A 验证输入并传给组件 B。比较 A 产生的确切保证与 B 的假设，包括截断、类型强制转换、规范化、租户范围和插件/扩展访问。
- **二阶使用**：存储时安全的数据在后续上下文中可能变得危险。字段名变成 JSON 路径，slug 变成文件路径，转义文本进入原始渲染，或存储的字符串变成 URL、正则、模板或策略表达式。
- **范围和能力增长**：令牌、API 密钥、插件、OAuth、MCP 或 AI 能力在委托、刷新、缓存、角色变更或组合后变得更广。指明结果主体本不应拥有的具体操作。
- **时序和顺序**：审查设置、迁移、软删除、撤销/缓存过期、检查/使用和验证/消费窗口。报告前确认陈旧状态被接受。
- **回滚和恢复**：取消删除、恢复、修订回滚和取消必须应用当前所有权、验证和授权。确认恢复了哪个无效状态。

**通配**（subagent_type: `general`）
不给你类别。寻找已分配标准类别之外的漏洞。

阅读看起来无聊或与安全无关的代码。跟进不完整的、实验性的、兼容性和回退功能，但保持与其他所有类别相同的具体边界和验证要求。

使用这些起点，但不要局限于此：
- 代码库中最奇怪的代码是什么？为何存在？被滥用会怎样？
- 是否有感觉半成品、实验性或硬加上去的功能？这些安全性最弱，因为审查最少。
- 以 UI 绝不会用的方式使用 API 会怎样？UI 约束用户，但 API 不约束。哪些 API 调用可能但客户端从不发起？
- 是否有隐藏或未文档化的端点、参数、头部或功能？查看路由注册、中间件和配置中不在文档里的东西。
- 混合本不设计一起工作的功能会怎样？本地化 + 预览 + 缓存。导入 + 插件 + Webhook。OAuth + 模拟 + API 密钥。
- git 历史中有何有趣之处？被回退的安全修复、被注释掉的认证检查、提交后移除的密钥（仍在历史中）。
- 哪些有效账户操作影响其他用户、共享完整性、可用性或运营方承担的费用？验证这些操作周围的遏制、配额、授权和恢复。
- 哪些操作不可逆或需要提升确认？将授权和审批绑定到最终主体、操作和资源。
- 代码对环境做了哪些假设？数据库是本地、时钟准确、DNS 可信、文件系统区分大小写？
- 查看测试文件 — 它们**没有**测试什么？比较开发者考虑过的边界情况（有测试）与未考虑的（无测试）。

在分配范围内追查异常，直到不变量确定。如果某处看起来奇怪，读到能说明它是否安全为止。如果函数有注释解释为何安全，验证该解释。如果变量名为 `temp`、`hack` 或 `legacy`，仔细阅读。

**显而易见的事**（subagent_type: `general`）
其他智能体寻找细微 bug。本智能体检查因人人假定别人已检查而容易忽视的基本暴露：
- 源码中是否有硬编码密码、API 密钥、令牌或密钥？（grep `password`、`secret`、`apikey`、`token`、`Bearer`、`-----BEGIN`、常见默认密码）
- 是否有引用安全的 TODO/FIXME/HACK/XXX 注释？（`TODO: add auth`、`FIXME: validate input`、`HACK: skip permission check`）
- 调试模式/开发模式是否正确门控？能否通过环境变量、查询参数或头部在生产中启用？
- 是否有在生产中有效的测试/示例/种子凭据？
- 是否有未受保护的 `/debug`、`/admin`、`/test`、`/status`、`/health`、`/metrics`、`/env`、`/.env`、`/config` 端点？
- 仓库中是否检入了 `.env`、`.env.local`、`credentials.json`、`*.pem`、`*.key` 文件？
- `.gitignore` 是否实际覆盖了密钥、上传和本地配置？
- 依赖是否锁定？依赖树中是否有已知 CVE？（检查锁文件）
- 是否有带动态输入的 `eval()`、`exec()`、`child_process`、`Function()`、`vm.runInContext`、`import()`？
- CORS 头是否设为 `*` 或过于宽松？`Access-Control-Allow-Credentials` 是否与通配来源组合？
- Cookie 是否缺少 `HttpOnly`、`Secure` 或 `SameSite` 属性？
- 是否有开放重定向？（名为 `redirect`、`return`、`next`、`url`、`goto`、`continue` 的参数未经验证就进入重定向）
- TLS 是否强制？是否有仅 HTTP 的端点？
- 生产中的错误响应是否返回堆栈跟踪、内部路径或 SQL 错误？

本智能体不需要创造性。它需要彻底和字面。检查每一项。报告每个结果。

**重要**：本智能体报告的任何发现都必须验证完整代码路径，而非仅表面现象。如果 Cookie 缺少 `HttpOnly`，检查该 Cookie 是否包含安全敏感数据，以及 JS 是否按设计需要读取它。如果错误消息包含字段名，检查该字段是否实际填充敏感数据。标记不是发现 — 报告前追踪影响。
