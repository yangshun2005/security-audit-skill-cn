# 安全审计

找出真正违反信任边界的漏洞，然后向负责人提供源码证据、安全复现方式、优先级和最小有效修复。这是防御性、源码优先的工作流。若候选问题没有具体的受影响主体、资源或安全后果，就不算已确认的发现。

## 运行模式

本技能默认仅提供指导。加载本技能并不授权执行完整审计工作流或创建文件。

- **指导模式**：对于安全咨询、专项审查、方法论、分类或特定发现的调查，只使用本技能的相关部分。不要自动运行全部六个阶段、创建输出目录或写入审计文件。需要时可以启动专项 agent；它们将结果返回当前任务。
- **完整审计模式**：当用户明确要求审计或渗透测试代码库，要求完整、全面或端到端的安全审查，或要求产出报告文件时，使用完整工作流。运行全部六个阶段并写入下文定义的文件。

如果请求可能属于任一模式，在创建文件或启动完整工作流前，先问一个明确的问题。

## 平台术语

本技能与具体 agent 平台无关：

- **Parent** 是协调本次运行并持有共享状态的 agent。
- **Task tool** 是平台的委派或子 agent 机制。
- **`research` agent** 是负责专项源码探索和事实核验的委派 agent。
- **`general` agent** 是负责广泛调查和有界本地执行的委派 agent。
- 标题中的 **`subagent_type:`** 指明该工作由这两种委派 agent 角色中的哪一种执行。

使用平台等效能力，同时保持角色、写入隔离、提示词和独立性边界。

## 通用执行安全

这些规则在两种运行模式下都适用。源码检查是只读的。仅在提供以下全部控制的操作系统强制沙箱内，运行目标代码控制的构建、测试、进程、浏览器、模拟器、模糊测试器和测试夹具处理：

- 无外部网络；仅当检查需要本地客户端/服务器流量时，使用隔离的 loopback 命名空间；
- 空环境，仅从显式允许列表填充安全值，并使用临时本地 `HOME`、临时目录和缓存；
- 只读的目标和工具链，目标代码控制的进程只能写入其分配的 `scratch/` 目录；以及
- 显式的低 CPU、内存、进程、文件大小、磁盘和挂钟时间限制。

在目标代码控制的进程之外，当构建必须写入源码旁时，agent 可以在分配的 `scratch/` 目录中创建一次性源码副本。在指导模式下，不要保留目标代码控制的文件。在完整审计模式下，只有可信的 parent 侧代码可以按照写入隔离中的流程，将最小的非机密结果提升到保留的 `artifacts/`。绝不要向目标代码暴露保留的输出目录（agent 自己分配的 `scratch/` 除外）、其他 agent 的目录、主机主目录、凭据、套接字或共享服务。不要安装依赖或让构建获取依赖。只使用本地已有的工具和依赖。如果无法强制执行每一项控制，就不要执行目标代码：将缺失的沙箱能力报告为 needs-validation 阻塞项，并提供安全的验证计划。

使用虚拟主体、测试夹具和密钥。不要探测已部署的端点、外部服务、共享基础设施、生产身份、其他用户的数据或实时控制平面。不要针对实时或共享进程测试可用性、发布构建产物、更改发布版本、消耗付费 API 配额，或超出建立缺陷所需的最小本地影响。如果决定性事实在源码或沙箱化测试夹具之外，将其报告为需要验证。

## 完整审计设置

在完整审计模式下，在侦察前确定以下值：

- **技能目录**：包含此 `SKILL.md` 的绝对目录。
- **目标**：被审查的绝对仓库根目录。
- **仓库名称**：从目录或本地 Git 远程获取的稳定仓库标识符。
- **输出目录**：目标之外的新可写目录，默认为 `~/security-audit-skill/<repo-name>/run-<N>`，其中 `<N>` 是下一个未使用的整数。仅当用户明确选择目标内的目录，且 parent 验证版本控制忽略整个目录时，才使用目标内的目录。否则停止并请求外部路径。
- **源码引用**：被审查的提交以及工作区是否脏。不要将未审查的生成或修改文件视为另一个修订版本。

### 写入隔离

Parent 创建共享运行文件，并且是唯一写入者：

- `run-metadata.json`
- `architecture.md`
- `coverage-ledger.json`
- `findings.json`
- `REPORT.md`
- `FINDINGS-DETAIL.md`
- `NEEDS-VALIDATION.md`

每个 hunter 或 verifier 在 `<output-dir>/agents/<agent-id>/` 下获得唯一根目录，其中包含独立的 `scratch/` 和 `artifacts/` 目录。规范 agent ID 匹配 `^[a-z0-9][a-z0-9_-]{0,63}$`，且不得等于 Windows 设备名，如 `con`、`prn`、`aux`、`nul`、`com1` 到 `com9` 或 `lpt1` 到 `lpt9`。小写 ID 可防止大小写折叠冲突。agent 和每个目标代码控制的进程只能写入 `scratch/`；保留的 `artifacts/` 归 parent 所有，绝不暴露给沙箱，且仅由可信的 parent 侧提升代码写入。Agent 不得更改共享文件、目标源码、保留的构建产物或其他 agent 的目录。不要使用 `/tmp` 或主机主目录作为可写回退。

在执行前，parent 打开并保留 agent 的 `scratch/` 和 `artifacts/` 根目录的可信、不可继承目录描述符，并记录预期 scratch 相对构建产物文件的允许列表以及显式的单文件和累计字节限制。绝不要将这些描述符传递给 agent 或沙箱。在沙箱及其所有进程终止后，可信的 parent 侧代码分别提升每个允许列表中的文件：

1. 验证声明的相对路径：拒绝绝对路径、空路径、`.`、`..` 或符号链接组件。
2. 从保留的 scratch 根描述符出发，使用不跟随的目录相对操作遍历每个父组件；绝不要按路径重新打开。
3. 以不跟随且非阻塞方式打开叶子节点。
4. 使用 `fstat` 验证它是常规文件，链接计数恰好为一，且在记录的单文件和累计字节限制内。
5. 从该描述符读取时再次强制执行这些限制。
6. 精确复制已验证的大小，重复 `fstat`，并拒绝身份、类型、链接计数或大小发生变化的情况。
7. 对于目标位置，从保留的 artifacts 根描述符出发，使用不跟随的目录相对操作遍历每个父组件；要求每个现有组件都是真实目录，并在重新打开并验证之前以独占方式创建任何缺失的目录。
8. 以独占方式创建叶子节点且不跟随链接，验证打开的目标是常规文件且链接计数恰好为一，并从已验证的源描述符复制，不重新打开任一端的路径。
9. 在非 POSIX 系统上使用等效的竞态安全 API。
10. 绝不要递归复制或通配 scratch、将归档解压到 artifacts，或打开/提升符号链接、FIFO、套接字、设备、目录、硬链接文件、正在变化的文件或超出其限制的文件。
11. 如果任何检查不可用、无法强制执行或失败，丢弃该 scratch 条目；如果它是决定性证据，保留 `needs_validation` 并附上确切的提升阻塞项。

[HUNTING.md](HUNTING.md) 和 [VALIDATION-AND-REPORTING.md](VALIDATION-AND-REPORTING.md) 将此流程作为 hunter 和 verifier 提示词中一个相同的围栏代码块，其规则和顺序与此列表相同。

对于复现的检查，记录命令、确切的测试输入、沙箱限制，以及仅允许列表中的环境变量名称和复现所需的安全非机密值。绝不要捕获或复制环境变量、继承变量、凭据值、认证状态或无关的主机路径。从空环境启动，而不是在执行后尝试脱敏。

在委派前，parent 写入 `run-metadata.json`，至少包含 `run_id`、`repo`、`target`、`source_ref`、`profile`、`scope_paths`、`budget`（未设置时为 null）、`execution_policy: "sandboxed-source-and-local-only"`、选定的配套文件、先前运行路径、共享文件所有者以及 `run_status: "in_progress"`。仅当这些事实变化时更新元数据；候选状态属于覆盖台账和 `findings.json`。

## 完整审计规划

本节中的覆盖、先前运行、配置文件和预算要求仅在完整审计模式下适用。

### 覆盖与先前运行

没有一次遍历是完整的。在狩猎前构建确定性的覆盖计划，并在每次 agent 结果后更新。[RECONNAISSANCE.md](RECONNAISSANCE.md) 定义了稳定的覆盖单元，[HUNTING.md](HUNTING.md) 定义了覆盖批评波次。只有 parent 更新台账。

如果存在先前运行，在规划当前运行前读取每个兼容的 `coverage-ledger.json` 和 `findings.json`：

1. 将相关当前源码与每个先前记录和单元比较。仅凭先前源码引用不足以证明路径未变。
2. 仅当先前 `confirmed` 记录的相关源码和条件未变，且其证据仍满足当前契约时，才将其带入当前候选集。将其链接到种子状态为 `planned` 的当前台账单元，保留其指纹，仅将该带入的根本原因排除在 hunter 之外，并将带入的记录送入当前最终验证路径；重新检查它的第 3 阶段 verifier 成为该单元的分配所有者，并将其移至 `candidate`。
3. 当先前 `confirmed` 记录的相关源码发生变化时，创建当前 planned 重新验证单元。不要将该记录放入 hunter 排除列表。仅当当前独立验证确立当前路径和结果时，它才保持 confirmed。
4. 将先前 `needs_validation`、`deferred`、`blocked`、`out_of_scope` 以及任何源码变化的单元作为当前工作。仍然外部的 `needs_validation` 记录只有在检查当前源码追踪并通过指纹链接到当前 `planned` 单元后才能带入，该单元的 verifier 重新检查提供其所有者和证据；该记录保留未解决的阻塞项。这些先前状态绝不抑制当前单元。
5. 先前同源已覆盖单元可以影响优先级，但它仍保留在当前台账中可见。先前 `rejected` 记录仅抑制未变化的失败声明，不抑制其单元的覆盖；变化的证据会产生当前工作。
6. 读取先前配置文件和范围。先前 `quick` 或限定范围的台账仅贡献其记录的证据和缺口，绝不隐含"其余没问题"。

如果不存在先前台账，在最终覆盖声明中说明。绝不要暗示一次运行就穷尽了目标。

### 运行配置文件和范围

在完整审计设置期间，根据用户请求选择配置文件，或根据目标的大小和风险提出一个。将其记录在 `run-metadata.json`（`profile`、`scope_paths`）中，并在报告中说明。默认为 `standard`。

- **`quick`** — 针对小目标、重新运行或快速初查的有界遍历。将台账单元粗化为表面 × 边界 × 攻击类别（子系统使用固定的规范标识符 `profile/quick/all-in-scope-subsystems`），恰好运行一个 hunter 波次，随后恰好一次最终覆盖批评遍历，并为每个候选使用一个全新 verifier 进行候选验证和最终记录验证。不要启动后续 hunter 波次：将批评者接受的发现和重新分配记录为 `deferred`。
- **`standard`** — 按所写的工作流执行。
- **`deep`** — 用于高风险或大型目标。按子系统和生命周期模式拆分台账单元，运行批评波次直到干净遍历，将候选验证和最终记录验证保持为独立的全新 agent，并为 `prior_covered_same_source` 单元提供独立的第二遍。
- **限定范围的运行** 审计子集：指定路径、一个子系统、一个配套域或两个源码引用之间的差异。仅为范围内的表面播种台账单元，将其他所有内容记录为 `out_of_scope`——绝不要记录为 `covered`。限定范围或 `quick` 运行必须表明自身为部分覆盖。

配置文件改变广度和冗余，绝不改变证据标准。不要缩减候选门槛、源码/本地执行边界、`needs_validation` 纪律、Schema 验证或 `confirmed` 记录的独立验证。

#### 成本预算

台账使花费可计数：一个单元大致对应一个 hunter 分配，一个存活的候选对应一到两个 verifier 分配，具体取决于配置文件。当用户设置预算——或 parent 为大型目标提出预算——在 `run-metadata.json` 中将 `budget` 记录为所有阶段中 agent 调用的最大次数。

在启动任何侦察 agent 前应用严格的预算门槛。保留四次基线侦察调用、`quick` 的一次最终波后批评者或 `standard`/`deep` 的一次波后加一次独立的最终干净批评者，以及至少一次 verifier 调用。仅在为每次额外调用重复此门槛后添加专项侦察。如果请求的预算无法资助该最低要求，不启动任何 agent：请求更大的预算、更窄的范围或不同的配置文件。如果请求保持不变，设置 `run_status: "incomplete"` 和 `incomplete_reason: "budget_cannot_fund_reconnaissance_and_reserves"`，并报告未运行任何审计遍历。

按以下顺序花费：

1. 将侦察、每次波后批评者和独立的最终干净批评者计为 agent 调用。
2. **在狩猎前保留批评者和验证。** 对于 `quick`，保留其一次波后最终批评者。在每次 `standard` 或 `deep` hunter 波次前，保留一次即时波后批评者加一次独立的最终干净批评者。还要从配置文件中保留 verifier 成本（每个预期候选约 1 或 2 个 agent；有疑问时保留批评者保留后余额的 30%）。绝不要将 hunter 分配到任一保留中。
3. 按优先级顺序将 hunter 分配到单元，直到狩猎配额用完。在该波次后立即花费保留的波后批评者；保持最终干净和验证保留不变。
4. 在后续波次前，再次保留其新的波后批评者。如果剩余预算无法覆盖所需的批评者调用和验证保留，不启动该波次的任何 hunter，将其计划单元标记为 `deferred`，原因 `budget_cannot_reserve_critics_and_validation`，并使用保留的最终干净批评者记录由此产生的缺口。

在波次 1 前，用播种单元、隐含 hunter 数量、强制批评者调用、验证保留以及剩余预算是否覆盖计划来更新侦察前估算。如果明显无法覆盖，说明并提出更紧的范围或更粗的配置文件，而不是悄悄稀释证据。如果后续事实消耗了所需的最终批评者保留，不启动 hunter，将所有计划工作标记为 deferred，设置运行 incomplete，原因 `critic_budget_exhausted`，且不做完整覆盖声明。

严格的 agent 总预算仍可能因意外大的候选集或需要另一个独立 verifier 的重大第 5 阶段替换而被超出。如果剩余预算无法验证每个候选，停止狩猎，在预算允许时按指纹顺序验证候选，并设置 `run_status: "incomplete"` 加 `incomplete_reason: "validation_budget_exhausted"`。将每个未验证的指纹链接到带有该未解决原因的 `candidate` 台账单元。不要将未验证的候选放入 `findings.json`，不要将其重新标记为 `needs_validation`，也不要报告运行完成。第 6 阶段仅当其第一节声明候选验证不完整并列出受影响的指纹和单元时，才可以生成部分报告。绝不要悄悄超出用户设置的严格预算。

## 核心原则

### 要求边界和结果

对于每个候选，指明较低信任的主体、接受的输入或操作、预期控制、跨越的边界、受影响的主体或资源，以及具体的已观察或所有者可观察的结果。不要将缺失的最佳实践、猜测的部署行为、通用解析器崩溃或自我影响提升为安全发现。

### 使用有界本地证据

静态分析确立源码路径。当所有执行控制可用时，沙箱化本地测试解决行为：最小函数测试夹具、现有单元测试、小型解析器测试夹具、虚拟租户集成测试、本地渲染的配置或有界隔离 loopback 客户端。在错误返回值、未授权的虚拟记录、sanitizer 发现、策略差异或其他最小影响处停止。不要将本地检查扩展到最小边界结果之外，或产生持久化、故障后或隐藏材料。

### 尊重源码可见性

部署控制、代理行为、提供商设置、浏览器头、身份策略、broker ACL、打包和拓扑都是真实控制。如果它们是必需的且不在仓库中，不要假设存在或不存在。使用 `needs_validation` 并附上确切的缺失事实和安全的 owner 观察或本地计划。

### 将优先级与确定性分开

只有 `confirmed` 记录获得严重性。可能性和影响必须反映已证明的条件和结果；总体严重性不能超过已证明的影响。`needs_validation` 意味着一个具体的、有源码依据的边界假设被阻塞，而不是低置信度的已确认漏洞，且它没有严重性。

使用以下锚点校准总体严重性：

- **critical** — 未认证行为者获得代码执行、完整数据存储访问或任意账户接管。
- **high** — 行为者完全击败具有真实后果的显式安全控制：认证绕过、跨租户读或写、影响其他用户的存储脚本执行、已认证代码执行或未认证远程停止共享服务。
- **medium** — 具有有限爆炸半径、不常见前置条件或后果局限于狭窄资源集的真实边界违反。
- **low** — 非机密内部信息泄露，或需要持续努力才能获得最小收益的影响。
- **informational** — 已确认但影响最小的观察，主要作为更大发现中的前置条件有用。

high/medium 区分标准：已证明的结果是完全击败具有真实后果的显式控制，还是仅削弱它？如果你无法说明具体损害，严重性低于感觉。

### 推荐最小有效源码修复

对于每个已确认的发现
